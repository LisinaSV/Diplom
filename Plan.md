# Plan.md — План тестирования и автоматизации приложения «Мобильный хоспис»

## 1. Цели
- Провести ручное тестирование мобильного приложения «Мобильный хоспис».
- Составить чек-лист проверок (Check.csv) и тест-кейсы (Cases.csv).
- Автоматизировать проверки UI-тестами (Appium + JUnit 4 + Kotlin).
- Подключить Allure и получить отчёт по результатам прогона (allure-results.zip).

## 2. Границы приложения
В scope:
- **Авторизация**: вход с валидными данными, выход (Log out), негативные сценарии (неверный логин, неверный пароль, пустые поля).
- **Лента новостей**: отображение списка карточек, раскрытие/сворачивание карточки, переход на экран ALL NEWS.
- **Управление новостями**: создание, редактирование, удаление новости; открытие формы создания/редактирования («+» и «карандаш»).
- **Сортировка новостей**: переключение и сброс состояния сортировки.
- **Фильтрация новостей**: экран фильтра (категория, начальная дата, конечная дата), фильтр по диапазону дат, по категории, только с начальной датой, только с конечной датой.
- **Главное меню**: навигация в раздел News (панель управления).
- **Тематические цитаты**: экран Our Mission с цитатами.

Вне scope (не реализовано в приложении / не проверяется):
- серверное API и интеграционные проверки;
- нагрузочное тестирование и тестирование производительности;
- локализация и международизация (приложение проверяется в единственной доступной локали);
- тестирование безопасности;
- функции, отсутствующие в сборке (push-уведомления, профиль пользователя и т. п.).

## 3. Типы тестирования
- Функциональное тестирование пользовательского интерфейса (UI).
- Негативное тестирование (некорректные и пустые данные авторизации и формы новости).
- Smoke-проверка (авторизация, главный экран, лента новостей).
- Регрессионное тестирование (полный прогон 24 автотестов).

## 4. Окружение
- Эмулятор: Pixel 4 AVD, Android 10 (API 29).
- Сервер автоматизации: Appium 2.x, адрес http://10.0.2.2:4723.
- Стек: Kotlin, JUnit 4, Appium Java Client (UiAutomator2), Allure (allure-kotlin + allure-android).
- Сборка: Gradle 8.13, Android Studio.
- Данные для авторизации: login2 / password2.

## 5. Этапы работ
1. Разведочное ручное тестирование приложения, определение границ.
2. Составление чек-листа (Check.csv) с отметками о прохождении.
3. Составление тест-кейсов (Cases.csv) с указанием покрытия автотестами.
4. Настройка проекта: зависимости (Appium, JUnit 4, Allure), директория androidTest, page-object'ы.
5. Написание UI-тестов: 24 сценария в классах MainFlowTest (20) и LoginNegativeTest (4), каждый шаг обёрнут в Allure.step и завершается проверкой.
6. Разметка тестов для отчёта: @Epic, @Feature, @Story, @DisplayName, @Description, @Severity; прикрепление скриншота при падении (TestWatcher).
7. Прогон и отчёт: сбор allure-results с устройства, генерация и проверка отчёта, упаковка в allure-results.zip.
8. Итоговые документы: README.md (запуск), Result.md (сравнение времени ручной проверки и автотестов).

## 6. Критерии готовности
- Все проверки чек-листа выполнены вручную, результаты зафиксированы.
- 100% проверок из чек-листа покрыто автотестами, кроме отмеченных с причиной.
- Прогон автотестов проходит без падений (кроме тестов, фиксирующих документированные дефекты).
- Отчёт Allure собран и приложен архивом allure-results.zip.

## 7. Документированные дефекты
- Баг-репорт №3: фильтр новостей с заполненной только начальной датой возвращает пустой список, хотя подходящие новости есть. Поведение зафиксировано автотестом testFilterStartDateOnly («Известный дефект»).
